# 对外令牌：按调用方签发、按权限授权

> 状态：生效中（2026-11-24 实现）。决策见 D-050。各接口契约的开通方式以本文为准；旧的单文件令牌仍可用，见「兼容」。实现：`server/agent_clients.py`（清单与热加载）、`server/agent_auth.py`（按权限鉴权）、`server/client_admin.py`（管理命令）。

## 背景：单文件令牌的问题

原来每类能力一枚令牌、一个文件（`listing-agent.token`、`trading-agent.token`、`collection-read.token`），一个实例每类只能有一枚，改动要重启。实际使用时：

- **一个 Agent 要拿好几枚**：完成闲鱼上架全流程，同一个 Agent 要同时配资料包令牌和交易令牌，第 4 步回执的路径在 `listing` 下却要用交易令牌，容易配错。
- **撤销会误伤**：订单监听器和上架 Agent 共用同一枚交易令牌，监听器所在机器出问题时，撤销令牌会连带上架 Agent 一起停掉。
- **每加一种能力就多一个文件**，采购评估还要再加第四个。
- **轮换要重启**。

## 设计

**一个调用方一枚令牌，令牌上挂权限。** 调用方是实际发请求的那个程序：你的上架 Agent、跑在路由器上的订单监听器、采购 Agent、手机快捷指令。

### 权限

| 权限 | 能调用 | 另需模块 |
| --- | --- | --- |
| `listing:read` | 查找库存、下载资料包 | 二手交易 |
| `trading:write` | 上架回执、付款订单、收货与到账 | 二手交易 |
| `collection:read` | 已购唱片查询 | 无 |
| `insight:read` | 采购评估（含是否已有） | 无 |

同一枚令牌也用于 MCP 入口 `POST /mcp`：连上后只看得到令牌权限对应的工具和场景模板，见 [MCP 接入](MCP接入.md)。

### 按场景的推荐配置

| 调用方 | 权限 | 理由 |
| --- | --- | --- |
| 上架 Agent（交互式，你在旁边看着） | `listing:read` `trading:write` | 一枚令牌走完上架流程第 1–6 步 |
| 订单监听器（无人值守、长期在线） | `trading:write` | 暴露面最大，只给写事实的权限，出问题单独撤销 |
| 采购 Agent | `insight:read` | 只读汇总，不碰资料包和照片 |
| 手机快捷指令「查一下有没有」 | `collection:read` | 不含金额，丢了也没有财务信息泄露 |

同一个 Agent 既上架又采购，就给它一枚带三项权限的令牌；无人值守的程序始终单独一枚。原则是**按「谁在跑、跑在哪」分令牌，按「要做什么」配权限**。

### 存储与管理

- 所有调用方记在数据目录的 `credentials/clients.json`，权限 `0600`。只存令牌的 SHA-256，不存明文；字段为 `name`、`scopes`、`sha256`、`createdAt`。
- 用命令行管理，在仓库根目录（Docker 内为 `/app`）以 Obi 服务用户执行。`--data-dir` 指向数据目录；省略时读取环境变量 `DATA_DIR` 或 `OBI_DATA_DIR`（Docker 镜像已设为 `/data`）：

  ```sh
  docker compose exec obi python3 -m server.client_admin add 采购Agent --scope insight:read
  python3 -m server.client_admin --data-dir /srv/obi/data add 订单监听 --scope trading:write
  python3 -m server.client_admin --data-dir /srv/obi/data add 上架Agent --scope listing:read --scope trading:write
  python3 -m server.client_admin --data-dir /srv/obi/data list            # 名称、权限、创建时间；也列出旧令牌文件
  python3 -m server.client_admin --data-dir /srv/obi/data scopes 上架Agent listing:read trading:write
  python3 -m server.client_admin --data-dir /srv/obi/data rotate 订单监听  # 换新令牌，旧的立即失效
  python3 -m server.client_admin --data-dir /srv/obi/data revoke 订单监听
  python3 -m server.client_admin --data-dir /srv/obi/data import-legacy
  ```

  令牌只在 `add` 和 `rotate` 时打印一次，存进 Agent 的密钥配置；丢了就 `rotate`。

- **不用重启**：服务器每次处理对外请求时检查 `clients.json` 的修改时间、大小和文件编号，变了就重新读取。撤销立即生效。管理命令以原子替换写入，服务器不会读到写了一半的文件。
- **失败即关闭**：手工改坏 `clients.json`（格式错误、名称或摘要重复、未知权限）时，服务器拒绝全部调用方并在日志中说明原因，不沿用旧内容；管理命令也会拒绝在坏文件上继续操作。
- 令牌格式统一为 `obi_client_` 加 43 位随机串；名称 1–40 字，实例内唯一。

### 鉴权结果

| 情况 | 状态 |
| --- | --- |
| 没有任何调用方具有该接口所需权限 | 404（接口未开通，和现在一致） |
| 缺少令牌或令牌不存在 | 401 |
| 令牌有效但缺少该接口的权限 | 403，`error` 说明缺哪项权限 |
| 需要的模块未开启 | 400（和现在一致） |

### 兼容

- 旧的三个令牌文件继续有效，视为固定权限的调用方，旧令牌在其他权限的接口上返回 401，行为与原来一致：`listing-agent.token` → `listing:read`，`trading-agent.token` → `trading:write`，`collection-read.token` → `collection:read`。仍需重启才能识别。
- `import-legacy` 把旧文件迁移进 `clients.json`，调用方名为「旧令牌 listing-agent」等，保留原令牌，不需要改 Agent 配置；确认可用后删掉旧文件并重启。
- 迁移完成一个版本后，契约文档改为只介绍新方式。

## 不做的事

- 不做网页上的令牌管理：签发令牌是服务器管理员的操作，留在命令行。
- 不记录每次调用：不写最后使用时间，避免每个只读请求都写数据库。
- 不做令牌过期时间：个人实例靠轮换和撤销即可。
