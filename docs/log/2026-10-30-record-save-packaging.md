# 2026-10-30 · 编辑保存链路诊断与实物包装必选

用户报告添加照片后保存长时间转圈，以及资料库不提供形态时没有明显补选入口；用户进一步确认：必须选择包装后才能保存。

## 完整链路与耗时边界

| 阶段 | 实际路径 | 诊断 |
| --- | --- | --- |
| 选照片 | `core/photos.ts` → `PhotoQueue` → HEIC 解码 / 1600 长边 JPEG（质量 0.82） | 在保存之前进行；缩略图只是本地 data URL，不代表上传完成。处理中会拦截保存。 |
| 点击保存 | `RecordForm` → `buildPayload` → `api('records')` | 新照片以 Base64 和表单一起 JSON 上传，约增加 1/3 体积；已有照片只传序号，不重新上传原图。当前只有整体转圈，没有上传阶段或百分比。 |
| 服务端校验 | `http.do_POST` → `routes.api_records` | 完整接收请求体、JSON 解码后进入写锁。条码 / 来源身份没变时跳过外网核对；换版或新增带条码版本才再次核对。封面匹配发生在保存前，忙时会拦截提交。 |
| 写入 | `Store.save` → `prepare_photos` → DB 提交 → `apply_photos` | 照片 Base64 解码并落文件；保留的照片也会读取后重写。正常小规模本地写入不是秒级瓶颈，未据此重构存储。 |
| 返回上一层 | `useFormSubmit({backOnSave:true})` → `app.refresh` → `/api/state` → `record_rates` | 编辑保存会等待刷新完成再返回详情；因此保存按钮转圈包含上传、写入和刷新三段。刷新补取汇率可能联网。 |

固定 21 副本离线样本，4 份 350 KB 字节载荷：1.40 MB 照片变成 1.87 MB 请求，序列化约 3.7 ms，保存约 5.3 ms，缓存正常的 state 约 0.7 ms。该载荷只用于隔离 Base64 / 写盘，不代表实拍图片内容或手机性能。

浏览器另用固定样本库的真实参考图集走选图 → 压缩 → 保存 → 详情回显：8 张 JPEG 合计约 3.72 MB，POST 约 4.96 MB，本机请求约 73 ms（首字节约 25 ms），后续 state 约 6 ms。再保留前 4 张保存，载荷为序号 `[0,1,2,3]`、约 1.3 KB，请求约 8 ms。参考图片不是用户实拍，不构成品相 / 版本核验。全部网络数字是本机回环，不代表 4G；例如 1 Mbps 上行发送 4.96 MB，单纯传输理论上约 40 秒。尚未取得用户那次手机请求记录，不能确定上传与刷新各占多少。

## 确定的问题与修复

`RateService.warm` 失败后没有记下失败日期；紧接着 `record_rates` 对每个日期调用 `get`，再次联网。下一次刷新又从头开始。每次真实请求有两个镜像，各 15 秒超时，多个日期会放大等待。

每次上游失败延迟 50 ms 的固定样本模拟：修复前一次刷新请求 8 次、约 466 ms，下一次又 8 次、约 446 ms；修复后首次 1 次、约 61 ms，下一次 0 次、约 1.7 ms。现在失败与空结果共用 5 分钟冷却，期满允许恢复；未取到汇率的成本仍为 null，不写 0。首次缺缓存的请求仍可能等待一次上游超时，本次没有改成后台汇率请求，也没有改变照片上传协议。

包装选择器移到「这一张」：缺失、来源未知占位、旧记录待核对直接展开；已知形态显示摘要并可展开更换。复用 `PackagingPicker`，以 `required` 隐藏「不清楚」，未选时保存定位并聚焦首个选项。保留既有包装和照片区域数据，不补猜形态。契约见 D-034。
