# 2026-10-28 · 长文案原位覆盖阅读

## 出现的问题
上架资料的文案可能很长，按原高度裁切只能看到开头，也没有明确的阅读入口。用户要求：点文案就把这块往下展开，把下方图片和设置盖住或收起；展开后必须能收起，且不能破坏原布局、出现跳动或抽搐。

## 怎么解决的
1. 不把阅读层插入文档流：`ListingCopyReader` 通过 portal 挂在上架页的 `.listing-reading-host`（抽屉正文的滚动容器），从文案顶部绝对定位到正文底部，背景用抽屉同色 `--surface`，直接覆盖照片、生成设置与核对依据；底栏在 host 之外，位置与可用性不变。
2. 正文放在独立滚动容器里，`overscroll-behavior:contain`；顶部常驻「收起全文」，Esc 只收阅读层，不触发抽屉关闭；收起后把焦点还给原摘要且不滚动。打开时只把 `.listing-body` 设为 inert，底栏复制/保存仍可点。
3. 展开与收起只做 `clip-path` 裁剪和透明度过渡，不做高度动画、不移动兄弟节点；原摘要一直留在原位，因此展开中途、滚到底再收起都不会重排。窗口尺寸变化由 `ResizeObserver` 重新量取顶部与宽度；`prefers-reduced-motion` 下直接切换。
4. 仅当摘要真实溢出预览高度时出现「展开全文」和按钮语义；点击时若有选中文本则视为选字，不误开。
5. WebKit 截图会由 Playwright 注入一张隐藏光标用的样式表，被 CSP 记一次样式拒绝；验收只忽略截图那一刻的这条固定文案，其他 console/pageerror 仍按零错误失败。该专项已接入 CI 售卖验收（主流程结束后向同一服务补写长文，再跑 Chromium 版）；WebKit 用 `OBI_READER_WEBKIT=1` 在本地补验。

## 验证
- Chromium 与 WebKit、390×844 与 1280×900 各跑一遍：展开后 25/60/130ms 三个时点原摘要、照片、底栏的 x/y/宽/高与正文滚动值均不变；正文滚到底再收起、快速反复开合、焦点恢复、Esc、减少动态效果、原页面已有滚动、横竖屏旋转后宽度对齐且无横向溢出；正常流程 console/pageerror 为零。
- 后端 497 项、前端 163 项、typecheck 与 build 通过；固定样本长文经 `seed_listing_long_copy` 写入，不使用一次性伪造正文。
- 截图：`/tmp/obi-listing-reader-shots`（Chromium/WebKit 收起与展开）。

## 证据边界
- 浏览器自动化证明布局与输入链路，不等于 iPhone / Android 真机的惯性与帧率表现；系统字体差异可能让预览裁切位置略有不同，但阅读层本身不依赖固定像素高度。
- WebKit 的 CSP 过滤只放行截图注入的那一条固定文案，不放宽应用自身的样式策略。
