### 写入与冷算实测（合成账本，单条元数据保存取 10 次平均）

| 账本规模 | 改一条记录 | 其中 `_album_catalog` 重建 | `state()` 冷算 |
|---|---|---|---|
| 300 张 | 7.6 ms | 3.1 ms | 6.9 ms |

## 2. 离理论最优还剩的差距（按值得程度排序）

1. **照片切换仍有极小的不一致窗口（中）。** 账本提交后才改名；两次改名之间照片目录短暂不存在。只有进程恰好在这几毫秒崩溃才会暴露。理论最优：照片按内容哈希命名、不可变，记录只存引用列表，账本提交是唯一生效点。`stash_cover` 已是这种做法，可照搬。
2. **再次打开时每个资源都要重新验证（中，需先查约束）。** 固定文件名 + no-cache + ETag，11 个资源 = 11 次 304 往返。理论最优是文件名带哈希、永久缓存，再次打开零请求。先确认安卓外壳与 Service Worker 对固定文件名的依赖能否放开。
3. **样式与公共代码不拆（低）。** `index.js` 315 KB + `index.css` 247 KB（gzip 约 101 KB + 44 KB），每页都下载；`cssCodeSplit: false`。按页拆 CSS 需先用 `@layer` 理顺层叠顺序。
4. **前端整树重渲染（低）。** 一个 AppContext 被 54 个文件使用，`memo(` 零处，叠加 8 s 轮询。规模小时看不出。
5. **写入 O(N)（低）。** 见 §1 表，上千张后再考虑。

## 4. 下一步（按投入产出）

1. **部署可重建**：ship 前检查是否落后远程；dirty 部署自动保存「基准提交 + patch + 文件哈希」。唯一真实存在的风险，改动最小。
2. **照片改为内容寻址不可变文件**：消除最后的不一致窗口。
3. **构建产物移出 git，CI 只构建一次**：同时解决仓库膨胀、diff 噪音、「改源码忘构建」。
4. **AGENTS.md 瘦身 + 规则转检查**：例如用 import 检查拦住组件 → 表单的反向依赖。
