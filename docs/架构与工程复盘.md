## 0. 一句话结论

账本规则（副本、状态、金额、审计）已经很稳；成本主要花在四个地方：**同步范围太大**（每次都全量算账）、**数据库和文件操作不是一个原子**、**手机交互层自绘太多**（抽屉 / 键盘 / 手势反复返工），以及**源码 → 构建产物 → 线上的一致性**（产物进 git、dirty 部署）。先收紧这些边界，比换技术栈收益高得多。

## 2. 模块地图与组合方式

### 2.1 全景

```text
                ┌──────────── 部署形态（同一套后端）────────────┐
                │ Docker / 裸机(ship) │ 浏览器 Pyodide │ 安卓 WebView │
                └─────────────────────┴────────────────┴──────────────┘
web/src (React 19, TS strict)                server (纯标准库)
 core/  纯逻辑：api、state-sync、search、      app.py      组装/CLI/启动
        format、photos、gestures、gallery数学   http.py     HTTP、安全头、登录、gzip
 components/ui/  通用单元件(可整目录拷走)        routes.py   72 条路由表（唯一扩展点）
 components/     业务组件                       context.py  Services 依赖注入
 pages/  每页一个 lazy chunk                     storage.py  1471 行：事务/审计/revision/
 forms/  抽屉表单与提交                                      迁移/成本利润派生
 state/  AppContext + useLedgerState 等          domain.py   金额、分摊、规则（Decimal）
 styles/ tokens → base → layout → 页面           covers/rates/security/backups
                                                server/*catalog  MB/Discogs/Deezer/iTunes
                                                server/listing_* 售卖 AI 多服务商
                                                server/engine_*  3D 插件协议
                         SQLite（records/sales/shipments/meta/audit，id + JSON blob）
                         data/photos、data/covers（内容寻址）
```

### 2.2 关键数据链

- **读**：`SQLite → Store.state()`（全表 `json.loads` + 汇率补取 + 成本/利润派生）→ `GET /api/state` → `state_sync.send_state()`（整份序列化 → sha256 ETag → 304 或行级 delta）→ `core/state-sync.ts` 拼回 → `useLedgerState` → `AppContext` → 页面筛选排序 → 卡片。
- **财务写**：表单 → `POST /api/records|sales|shipments|bulk` → 全局 `WRITE_LOCK` → Store 事务 + audit → 前端 refresh 全量 state。
- **元数据写**（D-035，最近才拆出）：`POST /api/records/metadata` → Store.save(metadata_only) → 返回规范化字段 → 前端 `applyMetadataSave` 本地合并，不碰汇率。
- **查询**：`/api/catalog/*` → 多源并发 → `release_merge` 精确合并 → 人选版本。
- **本机模式**：`fetch /api` → 专用 SW → BroadcastChannel → Pyodide Worker → **同一张路由表** → IndexedDB。这是整个项目最漂亮的一处设计：业务零分叉，差异只在 `local_entry.py` 抹平。

### 2.3 规则写了但没完全落实的地方（已核对源码）

- 前端分层「core ← components ← pages/forms，禁止反向」：`components/BulkBar.tsx`、`SaleCard.tsx`、`ShipmentCard.tsx` 直接 import `forms/`。
- 「根目录业务模块独立」：`storage.py:13` `from server import photo_uploads`——底层反向依赖上层。
- 「禁止模块级单例」：`routes.WRITE_LOCK`、`state_sync._snapshots` 都是模块级全局（多实例 / 测试并行时共享）。

## 3. 瓶颈与性能最佳路线（按收益排序）

| 优先级 | 环节 | 现状证据 | 方案 |
|---|---|---|---|
| **P0** | 照片原子性 | `Store.save()` 先提交 DB，再 `apply_photos()`：`shutil.rmtree` 旧目录后逐张重写（`storage.py` apply_photos）。中途失败 = 记录说有 N 张、磁盘上没有。ZIP 恢复同理 | 不可变文件（内容哈希命名，像封面那样）+ 事务里只切引用 + 事后回收旧文件。封面已经这么做了，照片照搬即可 |
| **P1** | 全量 state | ETag 是**算完整份状态之后**的 body 哈希：304 只省带宽，服务端每次照样全表解析 + 派生 + 序列化 + sha256。每次保存还会 `_album_catalog()` 全表重建专辑实体 | 维护一个持久「账本 revision」（每次写事务 +1，汇率/设置各一个版本号）；ETag 用 revision 组合，命中直接 304，不进 `state()`；派生结果按 revision 缓存 |
| **P1** | 写锁 | 全局一把锁，锁内可能联网核验、读全部保留照片 | 联网 / 解码 / 读图移到锁外，锁内只做 revision 复核 + 短事务。WAL 先别开：ship 的快照是直接复制主库文件，要先改成 `.backup` API（I-010） |
| **P1** | 首屏 | `lazyPage` 声明即下载、`pagesReady()` 等**全部 10 页**到齐才渲染：约 24 个资产、981 KB（gzip ≈ 312 KB）。`index.js` 314 KB、`index.css` 247 KB（关了 CSS 拆分）、`CHANGELOG.js` 80 KB（整份更新日志打进包） | 只等目标页，其余 idle 预取；CHANGELOG 改成按需 fetch 的静态 JSON；CSS 层叠顺序问题用 `@layer` 解决后再开 `cssCodeSplit` |
| **P1** | 汇率耦合 | 历史测量：保存 4 ms、刷新 1115 ms，其中汇率 1107 ms；两镜像各 15 s 超时、持锁联网 | 汇率变成独立后台任务 + 版本号，state 只读本地缓存；未知汇率保持 null（不变零） |
| **P2** | 照片传输 | 单张 ≤8 MB、每副本 ≤30 张，保存计划最坏持有 ~240 MB；缩略图读原图 | 保存时生成小图；前端 Blob/ObjectURL 替代 base64；逐张幂等上传（未提交的 `photo_uploads.py` 正在做这件事，方向对） |
| **P2** | 外部查询 | 3 源并发但等最慢的；MB 1.1 s / Discogs 2.5 s 节流 | 总截止时间 + 渐进返回 + 正负缓存（TTL）+ 同查询合并 |
| **P2** | 渲染与轮询 | ShelfPage 每次多遍全表 filter/sort；AppContext 一个大 value 覆盖全应用；巡游渲染 3N 张；插件状态每 8 s 轮询 | 记忆化 selector、拆 context（数据 / 动作）、视口窗口化、按可见性和活动自适应轮询 |
| **P2** | 构建与部署 | `static/assets` 构建产物进 git（触及 527 次），`.git` 164 MB；CI 多处重复构建 | 产物不进 git，CI 构建一次、同一制品贯穿验收→发布→回滚，记录 SHA-256 |

**纠正一处我自己的误判**：我最初以为静态资源是 `no-store`（vite 配置注释这么写），GPT 指出并经源码确认，`server/static_files.py` 实际是 `no-cache + ETag`（未变即 304）。注释已过时——这本身就是第 7 节「文档语义漂移」的一个现场例子。

## 5. 提炼：你的审美体系

从 AGENTS.md「用户已定案的 UI 偏好」、组件注册表和返工记录中归纳，这些是你**反复坚持、可以带到任何项目**的原则：

1. **主界面只留控件和数字，解释收起来。** `Disclosure` 折叠说明、设置页「少字图标化」、迷你手机实时预览代替文字说明。
2. **空间结构不能被破坏。** 抽屉只能向下收回，不允许横推；批量条悬浮不挤压布局；顶栏不动、内容淡入；表单一屏放完。
3. **同一种交互只有一份实现。** 所有滑块共用 `useSlidingThumb` + `--slide-ms/--slide-ease`；下拉统一自定义 Dropdown；左缘返回手势只有一份（D-025）；文字输入统一走 FocusInput。
4. **动效连续、可逆、不脉冲。** 扇形交接随拖动连续可逆，禁止逐张跳动或缩放脉冲；可见重叠处不许跳切 z-index；按钮没有全局按下位移。动效表达空间关系，不做装饰。
5. **状态不只靠颜色。** 注册表每个组件都有「非颜色的状态区分」一列；颜色只走 token；三态主题默认跟随系统。
6. **默认保守，高级能力显式开启。** 默认 2D，3D 仅在实体通过能力检查后出现；模块关闭只收入口，绝不删改数据。
7. **少录入但不误录入。** 条码优先、精确匹配，多候选必须人选，不允许按标题猜；自动化尊重人工输入。
8. **手机是主场景，桌面是管理台。** 展示以触屏为主；桌面常驻勾选，手机按需开启。

可以把这 8 条直接写成一份跨项目的 `DESIGN-PRINCIPLES.md`，配上 `components/ui` 作为实现参考。

- **红线前置**：金额 Decimal + 字符串传输、成本未知 = null、分摊守恒、零运行时依赖、CSP 无内联。一开始就锁住核心语义，后面几乎零返工。

## 7. 经验教训：下一个项目要避免的

1. **规则文件不要变成日志。** AGENTS.md 只有 148 行，却有 42 KB（单行动辄几百字），被改了 64 次；DECISIONS 60 KB、CHANGELOG 80 KB、复盘 37 KB、docs/log 一个月 218 份。AI 每次都要读完这些，信噪比在下降。
   → AGENTS 只放红线 + 导航（目标 < 8 KB）；具体 UI 定案放到对应组件旁的契约文件或测试里；**能用测试 / lint / 闸门表达的规则，就不要写成文字**。
2. **文档会悄悄过时。** vite 配置注释说 no-store，实际是 no-cache + ETag；legacy 清单里有已不存在的条目。`check_docs.py` 只校验路径，校验不了语义。→ 少写描述实现细节的注释，多写可执行断言。
3. **构建产物不要进 git。** `static/assets` 被触及 527 次，污染 diff 和 churn、让仓库长到 164 MB，还会出现「改了源码忘了构建」这一整类问题（AGENTS 里专门写了一条提醒）。→ CI 构建一次，同一制品贯穿验收→发布→回滚。
4. **dirty 部署要能重建。** `-dirty` 标识诚实，但说不清包里到底是什么；10/30 那次正式实例就带着一份未提交的键盘改动上线。→ 每次部署保存「基准提交 + patch + 文件哈希清单」，或者只从隔离 worktree 构建。（你的记忆里有「改完直接 --allow-dirty」这条偏好——可以保留速度，但建议让 ship 自动存 patch。）
5. **先验证交付链，再改功能。** 安卓沉浸改了几轮原生代码，最后发现旧壳没更新；打包清单漏了三个模块。→ 每种发布形态先做一个「改一个字，确认它到了设备上」的冒烟。
6. **不要先在宿主里做、再外移。** 3D 从宿主实现 → 插件化 → 删旧管线，耗了 34 次提交。AI 照片识别做完又整块删掉。→ 实验性大功能从第一天就放在插件 / 独立仓库里，宿主只定义窄接口。
7. **手机交互少自绘，先查平台原生能力。** 抽屉、键盘、边缘返回占了最多返工。每次自绘都要和 iOS/Android 的系统行为对抗。→ 先用原生（`<dialog>`、`visualViewport`、原生滚动）验证，确实不够再自绘；而且**只有真机能证明键盘行为**，浏览器模拟不算。
8. **测试对准行为，别对准源码字符串。** `web/tests/helpers/compiled-sources.mjs` 这种断言源码文本的测试会阻碍正常重构（它也是 churn 热点之一）。3D 的宿主 GL 测试 8 次只绿 1 次，最终交还引擎自己验收。
9. **单日大批量提交风险最高。** 10/21 一天 59 次提交，大功能 + 大量 UI 修补混在一起，后面几天都在擦屁股。→ 一个功能一个分支 / 一次验收，UI 微调攒批。
10. **AI 协作：用闸门代替追加规则。** 复盘里的核心教训是「反复提醒同一条规则」。规则越追加越长，AI 越容易漏读；把规则变成会失败的检查（lint、测试、ship 预检），比写进 AGENTS 可靠得多。
