# Obi 性能与可靠性 · 2026-11-04

> 后续实施：I-018 / I-019 / I-020 已加入修复与回归，详见[可靠性实施记录](log/2026-11-04-reliability-boundaries.md)。本文统计与故障探针保留分析时点口径。

基线及覆盖范围见 [架构全景](架构全景-2026-11-04.md)。性能最佳应解释为：在既定正确性、体验、资源与维护约束下，让用户关键路径最短，并把慢路径和失败限制在局部。这里没有一个脱离设备、数据量和网络的“理论最优版本”。

## 1. 本次测量，而非沿用旧数字

在当前 Mac 的临时目录，经 tools/seed_samples 的 seed / open_store 初始化 21 个固定副本，再用同一 RECORDS 定义通过 Store.save 扩展至 210、1,050 条。假汇率、无联网、无封面与新照片；扩展部分主要增加库存记录，不按比例增加成交单、包裹或不同专辑数量。

state 测量绕过响应缓存，每档 40 次；缓存 API 为路由函数加内存 handler，40 次；元数据保存每档 20 次，revision 逐次递增，计时不包括读取待编辑记录。P95 用排序后的样本位置计算。文件系统/OS 缓存已热，不是冷启动测试。

| 副本数 | state 计算中位 / P95 ms | 缓存命中 API 中位 / P95 ms | 元数据写入中位 / P95 ms | state 原始 JSON 字节 |
|---:|---:|---:|---:|---:|
| 21 | 0.479 / 0.494 | 0.137 / 0.383 | 1.185 / 1.773 | 55,608 |
| 210 | 2.077 / 2.161 | 0.134 / 0.147 | 4.123 / 4.405 | 187,677 |
| 1,050 | 9.060 / 9.446 | 0.137 / 0.190 | 17.161 / 18.441 | 772,999 |

结论有限而明确：库未变时的指纹缓存有效；变更后的计算与保存仍随记录数增长。当前结果不支持优先迁移数据库，也不能证明公网首屏、手机动效、海量不同专辑或 Pyodide 速度良好。API 数字不含 socket、登录验证、gzip、网络和浏览器渲染。

## 2. 两个已经复现的可靠性问题

### 完整恢复与照片保存是两套提交协议

server/archive.restore 先校验并解包，再调用 Store.restore_backup 提交账本，随后逐个移动照片/封面/实体目录。它没有沿用单副本照片的前滚日志。

复现：两个临时实例均使用 seed_listing_photos；A 导出，B 导入，在目录切换的 shutil.move 注入 OSError。结果：B 已是 A 的记录 ID，记录声明有 2 张照片，但 A 的照片目录不存在，B 的旧照片目录仍在。重新打开 Store 后仍如此。

这是确定的故障处理缺口，**不是观察到真实用户数据已损坏**。坏 ZIP 的“校验失败不改数据”测试不能证明提交后的 I/O 失败也安全。

建议先扩展已有前滚日志思想到整个 restore：校验完毕，持久化恢复计划与阶段信息，保留新旧资源目录，明确恢复后可继续前滚或恢复旧账本，启动时处理未完成计划。每个阶段注入退出/磁盘错误。不要仅在 except 中复制一次旧库：那无法覆盖进程退出。

### 本机持久化失败仍回复成功

static/local/engine-worker.js 的 persist 调用 FS.syncfs(false, () => resolve())，忽略 callback 的错误参数。serve 等到了 Promise 完成，但没有等到“成功写入 IndexedDB”的保证。

复现：Node VM 加载当前 Worker 文件，用 FS.syncfs 替身回调 Error，模拟业务返回 200；最终仍向页面发送 200。这里证明的是错误传播缺失，不是浏览器真实配额耗尽现场。

建议：正确传播持久化错误，保留可重试状态并区分“内存已修改”与“持久化已确认”；失败后同步队列仍可继续，不能让一次 reject 永久毒化链条。不能直接让用户重试非幂等业务写：前一次可能已在内存完成，应重试同步并核对结果。具体 API 机制参见 [Emscripten FS.syncfs 文档](https://emscripten.org/docs/api_reference/Filesystem-API.html#FS.syncfs)。

## 3. 各环节瓶颈与下一步

| 环节 | 当前事实或风险 | 优化顺序与约束 |
|---|---|---|
| 首屏 | 当前页按需等待；首屏出现后立即预取全部页面，可能与封面竞争网络/解析；公共 CSS 仍整包 | 先测目标入口；按空闲、网络与用户意图限制预取；再以保持层叠顺序为前提拆 CSS。更新日志已延迟，不再列为未修项 |
| 元数据编辑 | 已避开汇率；仍全表重建 _album_catalog，并扫描受影响记录；照片暂存/读取在保存范围内 | 先保留已验证边界；若写入 P95 超预算，按受影响专辑增量处理，照片计划改引用，保持 revision 和共享备注一致 |
| 财务写入 | shipments 等路由外层持 WRITE_LOCK；to_cny → rates.get 可同步联网 | 锁外获取不可变报价快照，锁内再次核验业务 revision；不能把缺汇率算成零，也不能默默换日期 |
| 状态同步 | 指纹命中很快；meta 任意写都可使缓存失效；缺失日元汇率会令缓存不采用；delta 仍需完整计算当前状态 | 先测失效原因；有必要再维护领域版本，不能改成仅记录 revision 而漏掉汇率/设置；WAL 前必须同时更换指纹方案 |
| 汇率 | warm 已跳过覆盖日期；新日期仍持 rate lock 请求网络；status 只是 count/latest | 明确刷新任务与数据版本；若未来允许改写同一天报价，缓存键必须反映内容变化；这是改进设计，非已复现错误 |
| 条码/编号 | 服务端总期限 20 秒，但每请求新建线程池，超时后任务继续；重复查询可能叠加后台工作 | 有界共享执行器、同键请求合并、成功/空结果/失败分开 TTL；渐进结果可降低首个候选时间，但最终身份合并和排序需稳定 |
| 本机查询 | _Inline.submit 同步执行，直到任务完成才返回 Future；20 秒期限不能中断它 | 适配层传递剩余总预算或重做异步调度；不能仅换进度条。两次 20ms 模拟调用，deadline=1ms，实测仍约 58ms 后返回 |
| 取消 | 前端取消可丢弃迟到结果；不等于后台 HTTP/模型/线程已取消 | 显式区分 UI 取消与计算取消；继续后台缓存也可，但必须有并发与时间上限 |
| 照片 | 两路幂等暂存减少重复上传；前端仍 data URL→bytes→Blob；staged_bytes 仍读取整个文件；30×8MiB 为允许上界 | 优先用 Blob 生命周期和单张内存上限；保留图用链接/路径，新图也避免整组 bytes；不要声称当前始终只持一张照片 |
| 图片显示 | api_photo 读整张原图，未生成专用缩略图；手机取图可能预取原图 | 缩略图与原图分开缓存和请求；大图只在查看/分享需要时取。服务器零依赖下先评估客户端派生缩略图与可信校验，不直接引入图像运行库 |
| React | 每次 App render 新建宽 ctx；插件可见时每 8s 请求并 setStatus；用到上下文者受影响 | 先对相同插件状态保留对象，再稳定 actions、分离订阅域；只加 memo 无法隔离变化的 Context，见 [React 文档](https://react.dev/reference/react/useContext#caveats) |
| 展示/手势 | 多布局复制、运动帧、测量与层叠，设备决定 CPU/GPU 瓶颈 | 真机测长帧、像素面积、DOM 数与解码内存；离屏停动效，窗口化只在保持连续空间和手势语义后采用 |
| AI 写作 | 首次核对+生成两次推理；服务端任务串行且内存保存，本机 inline 会占 main Worker | 优先复用与输入摘要绑定的核对结果；有需求才持久化任务。缩短提示不如少一次重复推理；不牺牲事实或自动换计费来源 |
| 备份导出 | 先读账本、遍历哈希、再写 ZIP；缺共同快照锁；最后 out.read 将整包读成 bytes | 先保证账本与资源的同一时点，再从临时文件流式发送；哈希与打包间发生修改是源码可见风险，尚未并发实测 |
| 插件 | 安装后 hook 自动加载 runtime，不只在用户打开 3D 时加载 | 先测未进入展示页的加载成本；若显著，状态探测与运行时激活分离，保证卸载/恢复生命周期 |
| 交付 | CI 的 web 制品已共享给后端与浏览器；实际 ship 仍本机重建 | 从已保存源码树构建，验收并发布同一包，记录内容哈希；不同产品（Docker/APK）分别建立来源链 |

“本机共用后端”最容易掩盖资源约束。main/net 两 Worker 隔离了部分网络，但状态派生所触发的汇率、艺人资料、安卓售卖仍在主执行路径；不能把“有第二 Worker”当作完全解耦。

## 4. 三个不能一笔带过的取舍

**数据库。** 目前 rollback journal 与文件头指纹、ship 直接复制主库是成套约束。WAL 不是一行开关：先改快照/恢复与缓存指纹，再测收益。数据库快照可参考 [SQLite Backup API](https://www.sqlite.org/backup.html)，但它只解决数据库，不自动解决照片与数据库的一致时间点。

**静态缓存。** 稳定文件名 + no-cache + ETag 是当前明确契约。哈希文件与 immutable 可减少重验证，但需要同时调整旧页面的 chunk 加载、SW、APK 补丁、回滚和测试。不能说“改了文件名就零请求”：HTML、登录与业务状态仍需相应处理。

**照片方案。** 内容寻址不可变资产适合新项目，便于去重、缓存、引用切换和垃圾回收；当前项目已有日志恢复，改磁盘布局会牵动所有读取、下载和备份路径。不应仅因形式更漂亮就立刻迁移；优先补完整恢复的真实缺口。

## 5. 如何可验证地追求最佳性能

先定义并测四个用户指标：首次可操作、资料保存确认、查版首个可用结果/全部来源结束、手机手势帧稳定性。分别记录冷/热缓存、服务器/浏览器/安卓、稳定/慢网/离线。

建议的初始预算（讨论用，不是已达到或已定案）：热态纯资料保存服务端 P95 <100ms；参考网络下点击到确认 <500ms；缓存状态处理 <5ms；60Hz 手势每帧总预算约 16.7ms；目录来源必须有明确失败上界。预算需按真实手机和部署机器校准。

埋点应沿链路记录 requestId、客户端压缩/上传、代理接收、锁等待、数据库事务、外部请求、序列化、前端合并/绘制；只记耗时、大小、结果码，不记录模型令牌或私人文案。汇率、查版、照片、模型、备份各有独立 span。

优化顺序：减少不必要工作 → 缩小更新范围 → 缓存正确结果 → 合并重复请求 → 有界并发 → 再调底层实现。每项以同一基线和样本比较 P50/P95、峰值内存、失败率；平均耗时下降却增加错误成功响应，不能算性能提升。

## 6. 当前优先级

1. P0：修复本机持久化错误传播与完整归档恢复协议，补阶段故障注入；先保障“成功”是真的。
2. P1：发布从不可变源码快照构建并对齐包哈希；补数据库+文件快照一致性。
3. P1：测真实首屏/保存链路；财务锁外取汇率；本机查询的总预算与主 Worker 阻塞治理。
4. P2：缩略图、照片内存、插件状态无变化不更新、查询同键合并及有界执行器。
5. P3：依据规模与真机证据再做目录增量、列表窗口化、Context 拆订阅和 CSS 拆分。

本次后端与前端现有测试全绿，但新故障注入仍失败，说明测试数量不能代替边界覆盖。Docker、浏览器视觉及手机实测没有重跑，因为此次未修改运行时代码；这些结论不能充当下一次修复的验收。
