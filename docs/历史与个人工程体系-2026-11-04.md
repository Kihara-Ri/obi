## 4. 可以提炼出的审美，不只是一套皮肤

| 原则 | 在 Obi 的具体表现 | 跨项目可带走的合同 |
|---|---|---|
| 任务结果优先 | 上架页先给可复制正文和照片，依据/风格收起 | 首屏展示用户要带走的结果；复杂配置逐步揭示 |
| 空间连续 | 顶栏固定、内容淡入；抽屉向下收回；浮条不挤压布局 | 每个层有明确空间归属，进入/退出可逆且不突然换容器 |
| 直接操作 | 封面就地放大，长文就地展开，少一次跳转 | 用对象本身作为入口，同时保留可识别的操作反馈 |
| 克制而不失辨识 | 中性基底、token 控色、图标/数字优先，状态有形状与文字 | 视觉简洁不能牺牲错误原因、可访问名称和未知状态 |
| 事实与解释分开 | 版本来源角标、未知成本、待核对项不写进买家正文 | 明确来源、确定性与人工采用；漂亮展示不抹平证据层级 |
| 用户控制权 | 多候选人选、手动录入出口、已写文案不自动覆盖 | 自动化提供可审阅候选；确认点与可撤销动作显式存在 |
| 同一动作同一手感 | FocusInput、滑块、折叠、左缘返回共享实现 | 行为合同先统一，业务参数由调用方表达 |
| 实物优先 | 独立副本、照片属于这一张、不同尺寸不强缩放 CD | 数字模型服从真实对象与资料，不反过来篡改对象 |

你的设计语言可以概括为“物件清楚、动作直接、空间连续、证据诚实”。这是建议的描述，并非替你新定品牌口号。也不能简化为 ai-kit 的“只用灰度”：D-002 明确保留品牌与语义色，约束的是使用 token。

需要防止两个极端：过度少字导致保存被禁用却不知原因；追求流畅动画导致实际业务状态被延迟或掩盖。动画可以预测运动，不能伪造网络进度或持久化成功。

## 5. 可复用资产的分级

| 资产 | 现在适合怎样复用 | 提炼前必须处理什么 |
|---|---|---|
| tokens + Seg/Dropdown/Combobox/Collapse/Switch 等 | 低成本，优先试点一个其他项目 | 清点 CSS 变量、字体、图标、可访问性与减少动态效果；不要原样复制所有专辑样式 |
| FocusInput 与边缘手势核心 | 中成本，作为个人移动交互内核 | 明确滚动容器/顶部层/焦点/取消/卸载合同，带 iOS 与 Android 真机案例 |
| Drawer/Lightbox/Toast | 先抽行为接口，再打包 | Drawer/Toast 有 AppContext 类型或运行依赖；灯箱有自有事件/挂载约定，不能称为拷目录即通用 |
| Decimal、分摊守恒、null 成本规则 | 纯函数与行为测试可先迁移 | 参数化精度与币种，不复制 CD 状态机；输入原额与正式记账责任分离 |
| revision + 元数据局部合并 + 迟到响应保护 | 高价值协议范式，中成本 | 定义冲突、重试、失效、全量恢复；不能只复制 fetch hook |
| ETag/delta 同步 | 在第二个全量小账本类项目试用 | 实例化快照与锁，参数化表/ID/顺序，测 delta 是否比整包更便宜 |
| 多源查询 | 抽节流、缓存、冷却、预算、同键合并；领域身份规则留项目 | 禁止为“通用”放宽精确匹配；本机并发语义要明确 |
| AI 核对→候选→采用 | 复用工作流合同与输入白名单 | 模型能力、凭据与计费隔离，任务输入快照、过期结果拒收；不要复制不稳定 OAuth 细节作为通用保证 |
| 内容寻址资产与完整备份 | 适合作为下一项目底层设计 | 先补恢复协议、跨资产快照、GC 与流式输出；当前实现还不是可放心发布的通用备份库 |
| Pyodide 本机适配 | 高成本参考模板 | 持久化成功、线程替身、取消、CORS、配额、源地址与 Worker 调度各自验收 |
| 安卓壳与签名内容补丁 | 中高成本，可独立演进 | 去产品标识，桥版本/能力协商、持久化源、签名、升级/降级/中断合同 |
| ai-kit ship、泄漏扫描、文档索引 | 已有跨项目雏形，优先改上游 | 把快照到包的来源链做实；本项目特有闸门通过配置/扩展接入 |
| Album Engine | 保持独立插件，不再搬回个人基础库 | 继续由引擎拥有物理、模型与素材合同 |

不复用：专辑/发行版/副本的全部领域结构、固定渠道与国家映射、CD 包装判断、目录来源的特定合并条件、整套 AppContext、整个 storage.py。它们可以成为案例，不应该成为其他项目的先验模型。

提炼顺序：先建立原则与验收案例，再选第二个真实消费者移植一两个稳定组件；两边都使用后才决定包接口。没有第二个消费者时保留项目内模块，避免建立一套没有使用反馈的“个人超级框架”。

## 6. 最值得避免的六类流程错误

| 历史链条 | 深层问题 | 下一个项目的防线 |
|---|---|---|
| MoneyField 某入口修步进，其他金额入口仍不提交 | 复用了外观，没有收敛行为与全部调用方 | 改共同规则前列消费者清单；回归覆盖所有入口；业务差异显式参数化 |
| 编辑慢：缓存汇率→仍耦合→独立 metadata 命令 | 用局部优化维持了错误调用关系 | 先画“这个操作应该触发哪些副作用”，再决定缓存和并发 |
| 安卓多轮沉浸修复，原生补丁实际未到设备（eb15a73） | 测的是代码，不是交付后的运行身份 | 先显示 shell/content/bridge 版本与来源，再开始调设备行为；自动拦原生补丁 |
| 3D 软件 GL 截图连续加等待，最终宿主不再承担引擎运动验收 | 测试责任跨产品边界，环境成本被误认作产品故障 | 宿主测挂载/生命周期/数据保护，引擎测几何/运动；保留少量真实集成验收 |
| 包清单漏 cjkvariants/musicbrainz/kana | 运行闭包分散在人脑维护的清单 | 对实际制品做隔离 import/启动；Docker、裸机、local、APK 各验证自己的闭包 |
| 规则反复追加、旧说明仍像现行结论 | 决策、历史、实现快照混写，读取成本越积越高 | 红线短、定案有入口、历史只留证据；能机检的变检查，同时保留测试盲区说明 |

现有 26 个前端测试文件依赖 compiled-sources，适合一部分结构约束，却容易把实现文本当行为。分层规则应静态检查；金额/同步用纯逻辑测试；抽屉/键盘/持久化用运行态测试。不要一刀切删掉源码检查，也不要让“字符串还在”成为功能通过的证据。

不要把 Git 提交数量本身当敌人。小而可回滚的提交有价值；应控制的是同一高风险链上未经验收的改动数量。也不要机械坚持一个文件 200 行就拆事务——规范应服务于边界与可理解性。

## 7. 个人工程体系应交付什么

建议形成五个小资产，而不是一套包办所有应用的框架：

1. **原则页**：8–12 条审美/工程原则，每条附正例、反例、验收方式；区分跨项目原则与某项目定案。
2. **交互内核**：token、输入、弹层、手势、过渡与焦点；所有状态明确进入、取消、打断、恢复和卸载。
3. **数据协议模板**：领域身份、命令/查询、revision、未知值、资产提交和恢复；保持业务模型可替换。
4. **运行适配模板**：服务器/浏览器/原生能力表，统一“不支持、不可用、未授权、执行失败”的区分。
5. **交付工具箱**：固定样本、各形态启动检查、不可变构建输入、包哈希、更新兼容检查和恢复演练。

建议流程：确认对象与不变量 → 列出消费者/副作用/运行环境 → 扩展固定样本 → 贯穿一条最小用户流程 → 故障与平台验收 → 固化共同接口 → 同一制品发布 → 把重复教训变闸门。每一步都应能说出“什么证据算过关”。

衡量体系进步可以用：同类问题复发次数、一次规则变更漏掉的入口数、真机反馈到复现时间、修复后再次打开的数据一致性、一次可验证交付的时间、脱离项目仍能工作的组件比例。不要只看测试数量、文档数量、抽了多少文件。

## 8. 具体行动建议

先修本次两个持久化缺口；接着把发布快照变成真正的构建输入，并给关键操作加端到端耗时。然后选择一个其他项目，把 tokens + 一个输入组件 + 一个弹层合同作为首次复用试点；暂时不抽 storage、整个应用壳或所有模型适配。

对新项目，第一天就明确对象身份、未知值、数据归属、插件边界和每种部署形态。对现有 Obi，尊重已经稳定的事务与交互，以真实复发问题决定提炼顺序。最值得带走的是“每一种用户承诺都有唯一责任方和可执行证据”这套做法。
